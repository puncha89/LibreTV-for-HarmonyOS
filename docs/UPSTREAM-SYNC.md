# 与上游 LibreTV 对齐记录

> 基线：本仓库 `5eaaa50`（2.3.6，2026-10-27）
> 上游：`LibreSpark/LibreTV`（Next.js 15 版）
> 原则：**只补上游有、鸿蒙缺的；鸿蒙多出来的（手势、离线下载、推荐源、多端适配）一律不动。**

## 一、这一轮补齐了什么

| # | 能力 | 上游做法 | 本仓库原来的情况 | 现在的实现 |
|---|---|---|---|---|
| 1 | 源数量上限 | sources 100 / liveSources 50 | 50 / 20，导入 TVBOX 单仓配置必被截断 | `SourceManager.MAX_VOD=100`、`MAX_LIVE=50` |
| 2 | 多页搜索 | `SEARCH_MAX_PAGES` 默认 5；首页读 `pagecount`，实际页数 = min(总页数, 上限)；页间并行，单页失败只丢该页 | 只抓第一页 | `CmsClient.searchPage()` 带 `pg` 参数并解析 `pagecount`；`SearchService.aggregate()` 分波并发（每波 8 个源）+ 源内分页并行；设置页新增「搜索深度」1/3/5/10 页 |

| 4 | 接口目录 source-catalog | 支持裸数组 `[{name, baseUrl, enabled}]` | 裸数组会被当成空源列表静默丢弃 | `SubscriptionParser.parseCatalog()`；`baseUrl` / `url` 混用直接报错而不是静默丢一半 |
| 5 | 长按倍速 | 移动端长按 3 倍速 | 2 倍速 | `PlayerPage.PRESS_SPEED = 3.0`（提示文案自动跟着变） |
| 6 | 影视榜单（hot-list） | 豆瓣五个周榜 + 百度热播，经 60s API | 无此推荐源 | 新增 `model/HotListClient.ets`；设置页新增「影视榜单」选项；首页分类条换成六个榜单 chip，隐藏筛选条、关闭分页 |
| 7 | 订阅自动刷新 | 每个订阅可选 关闭/1/3/7/14/30 天，失败 3 次自动暂停，单次最多刷 5 个、并发 2 | **完全没有订阅概念**，导入即散装成源 | 新增 `SubscriptionRecord` 模型 + `data/SubscriptionStore.ets` + `model/SubscriptionSync.ets`；源管理页新增「订阅管理」面板（周期、立即同步、删除）；`VodSource`/`LiveSource` 增加 `subId`；同步策略为「整体替换」 |

### 顺手修掉的一个既有 bug

`SettingsStore` 一直在发 `SETTINGS_CHANGED`，但 `IndexPage` 从来没监听。后果是：**在设置里改「首页推荐来源」，必须重启 App 才生效**。这一轮加了监听（按 `recommendSource` 是否变化判断，其他设置变更不干扰首页），否则第 6 项做完也是「点了没反应」。

## 二、明确没有对齐的部分（以及原因）

### 1. HTTP-FLV 直播 —— 放弃，不是工作量问题

上游 `/live` 页支持 HLS + HTTP-FLV，因为浏览器有 MSE，FLV 解封装是浏览器给的。
AVPlayer 不认 FLV 容器；要支持就得自己写 FLV 解封装 + H.264/AAC 解码 + 渲染上屏，等于在应用里重造一个播放内核。

**结论：这是平台能力边界，不做，也不在 UI 上留假开关。**

### 2. 跳过片头 / 中段 / 片尾

上游有完整的标记体系（Shift+I/O/S/E 打点、进度条着色、全剧自动跳过、撤销、试跳）。这项**技术上可做**，但需要改播放器、进度条绘制与续播存储结构，工作量约等于上面八项之和，且必须真机反复调试时间轴。本轮按约定不做。

### 3. 订阅自动刷新的语义差异（必须知道）

| | 上游 | 本仓库 |
|---|---|---|
| 触发 | 服务端常驻进程定时检查 | 启动 App、回前台、进入源管理页时检查 |
| 含义 | 「到点必定刷新」 | 「至少每 N 天刷新一次，前提是这期间打开过 App」 |

App 没有后台常驻进程，这是硬约束。面板上的说明文字已如实写出，不是隐藏差别。

### 4. 其他小差异

| 项 | 上游 | 本仓库 | 说明 |
|---|---|---|---|
| 服务端代理 | 有，带 SSRF 防护、可绕防盗链 | 无，客户端直连 | 上游能播的个别源，客户端可能因 Referer/Cookie 拿不到，属架构差异 |
| 源测试 | 支持批量测活 + 订阅级暂停 | 已补批量探活；订阅级暂停已补 | 已对齐 |
| 封面防盗链 | 服务端 `/api/proxy/` 转发豆瓣封面 | 直连 `img*.doubanio.com` | 豆瓣图床一般允许直连；偶发加载失败时无代理兜底 |
| 订阅管理边界 | 直播源多归属共享 | 删除订阅时按 `subId` 一并摘掉 | 同一条 M3U 被两个订阅引用时，删一个订阅会把源一起删。上游是引用计数，这里简化了 |

## 三、需要真机验证的点（按优先级）

> 这台机器没装 DevEco Studio / HarmonyOS SDK，以上改动**没有经过编译验证**，只有源码级自查。第一次 Run 时请重点看下面这些。

1. **编译**：`hvigorw assembleHap` 是否 0 错误。重点看 ArkTS 严格模式对新增文件（`HotListClient` / `SubscriptionStore` / `SubscriptionSync`）的类型推断。
2. **多页搜索**：搜索一个冷门片名，对比「搜索深度 = 1 页」与「5 页」的结果数量差异；留意搜索总耗时是否可接受（源多时每波 8 个）。
3. **订阅管理**：导入一个订阅 → 进「订阅管理」看是否建档 → 点「刷新：关闭」循环到 3 天 → 杀掉 App 重进，看是否触发同步。
4. **一键探活**：源数量多时留意是否整体卡顿（分波 4 个，点播与直播串行）。
5. **影视榜单**：设置里切到「影视榜单」，返回首页应立刻变成六个榜单 chip。60s 公共实例有限流，拉不到时会保留旧列表而不是白屏。
6. **导出 M3U**：源多时会串行拉每个 M3U，注意是否有超时；导出内容用 VLC 打开验证。
7. **发布为链接**：确认能拿到 `https://paste.rs/...`；拿不到会提示改用「导出订阅」手动托管。
